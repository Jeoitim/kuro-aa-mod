# 场景渲染比例调查

真正提速需要在游戏渲染 3D 场景前减少内部像素，再重建到原输出尺寸。
当前厂商档位仍属于事后重建，本轮没有加入宣称能降低游戏本体渲染成本的开关。

## 已确认

只读检查官方启动器与图形配置，没有找到公开的独立场景渲染比例设置。
实际存档加载后的 DXBC 参数布局却包含引擎内部的 `cb_scene`：

| 字段 | 字节偏移 | 大小 |
| --- | --- | --- |
| vpSize_g | 384 | float2，8 字节 |
| invVPSize_g | 392 | float2，8 字节 |
| resolutionScaling_g | 960 | float，4 字节 |
| lightTileWidthInv_g | 608 | float，4 字节 |
| lightTileHeightInv_g | 612 | float，4 字节 |

名字表明缩放相关的内部机制可能存在，但布局包含声明，不代表每个 shader 都实际使用这些字段，也不证明修改 float 会调整 CPU 端渲染目标分配。

## 下一项只读验证

`TraceRenderLayouts=1` 记录参数布局与有限数量的缩放使用点反汇编；`TraceRenderValues=1` 读取主场景 HDR 几何所绑定的常量。
值采样最多 24 次，每 120 帧至多一次，只读取，不写参数；GPU 常量读取会产生少量诊断性同步开销，不能用这一轮测量正式性能。

诊断文件保留在本机，不把游戏 shader 反汇编或原始资源加入仓库与便携包。

确认使用点后还需关联实际的颜色 / 深度目标、viewport、光照 tile 和后处理尺寸。
只有各部分一致，并能维持输出与 UI 分辨率，才可以进行低分辨率场景实验及 GPU 帧时间 A/B 检查。

## 本轮实际值与使用点

正常存档中得到 24 次 HDR 几何常量读取：目标与 viewport 均为 1920x1080，逆尺寸约为 0.000520833 / 0.000925926，resolutionScaling_g 为 1。
已使用该字段的若干全屏 VS 保持输出位置不变，只用它除以或修正纹理坐标；相关 PS 使用它修正屏幕采样的横向坐标。
因此不能把修改这个 GPU 常量本身当作降低场景渲染尺寸的提速方案，它也不能证明存在可直接调用的 CPU 端动态分辨率设置。
未修改常量或游戏资源。真正的场景降采样仍需继续定位渲染目标分配 / 视图完成出口，不能作为本轮已实现功能。
