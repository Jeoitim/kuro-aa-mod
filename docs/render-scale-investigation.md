# 场景渲染比例调查

真正提速需要在游戏渲染 3D 场景前减少内部像素，再重建到原输出尺寸。
当前厂商档位仍属于事后重建，本轮没有加入宣称能降低游戏本体渲染成本的开关。

## 已确认

只读检查官方启动器与图形配置，没有找到公开的独立场景渲染比例设置。
实际存档加载后的 DXBC 参数布局却包含引擎内部的 `cb_scene`：

| 字段 | 字节偏移 | 大小 |
| --- | --- | --- |
| vpSize_g | 384 | float2，8 字节 |
| invVPSize_g | 392 | float2，8 字节 |
| resolutionScaling_g | 960 | float，4 字节 |
| lightTileWidthInv_g | 608 | float，4 字节 |
| lightTileHeightInv_g | 612 | float，4 字节 |

名字表明缩放相关的内部机制可能存在，但布局包含声明，不代表每个 shader 都实际使用这些字段，也不证明修改 float 会调整 CPU 端渲染目标分配。

## 下一项只读验证

`TraceRenderLayouts=1` 记录参数布局与有限数量的缩放使用点反汇编；`TraceRenderValues=1` 读取主场景 HDR 几何所绑定的常量。
值采样最多 24 次，每 120 帧至多一次，只读取，不写参数；GPU 常量读取会产生少量诊断性同步开销，不能用这一轮测量正式性能。

诊断文件保留在本机，不把游戏 shader 反汇编或原始资源加入仓库与便携包。

确认使用点后还需关联实际的颜色 / 深度目标、viewport、光照 tile 和后处理尺寸。
只有各部分一致，并能维持输出与 UI 分辨率，才可以进行低分辨率场景实验及 GPU 帧时间 A/B 检查。

## 本轮实际值与使用点

正常存档中得到 24 次 HDR 几何常量读取：目标与 viewport 均为 1920x1080，逆尺寸约为 0.000520833 / 0.000925926，resolutionScaling_g 为 1。
已使用该字段的若干全屏 VS 保持输出位置不变，只用它除以或修正纹理坐标；相关 PS 使用它修正屏幕采样的横向坐标。
因此不能把修改这个 GPU 常量本身当作降低场景渲染尺寸的提速方案，它也不能证明存在可直接调用的 CPU 端动态分辨率设置。
未修改常量或游戏资源。真正的场景降采样仍需继续定位渲染目标分配 / 视图完成出口，不能作为本轮已实现功能。

另一条渲染阶段的路线是 [场景着色降载实验](scene-vrs-experiment.md)：使用 NVIDIA DX11 VRS 减少部分像素着色调用，不改变渲染目标尺寸。已通过硬件夹具和实际注入的调用数检查，但尚未确认游戏帧率收益。

## 渲染目标分配路线

用户在游戏中未观察到明显的 VRS 流畅度或 GPU 占用改善。VRS 保留为独立实验选项，不与质量、均衡、性能档位联动。GPU 占用百分比也不能替代同场景的 GPU 帧时间比较。

ReShade 的 `create_resource` 回调允许改写资源描述，`bind_viewports` 可观察视口；这些是底层拦截能力，不是游戏内部的场景倍率设置。
只改 HDR 颜色目标会与原尺寸深度、视口及后处理不一致；按尺寸统一缩小全部目标又会影响 UI 和独立视图。当前 AeonSR 入口负责收到画面后的重建，不能控制游戏之前的目标分配。

新增默认关闭的 `TraceRenderTargets=1` 诊断：

- `KuroUI-targets.csv`：颜色 / 深度目标的实际尺寸、格式、用途和游戏分配调用栈 RVA，最多 4096 条。
- `KuroUI-target-passes.csv`：每 300 帧抽取一帧，记录输出目标、深度、前 16 个像素 shader 输入、视口和游戏调用栈，最多 12000 条。

不读取像素、不复制 GPU 缓冲、不修改游戏参数；诊断仍有 CPU 与文件写入开销，不用于性能测量。
需要从启动时安装该组件，才能观察主目标创建。一轮正常加载存档即可，无需逐个打开菜单。

接下来按资源流关联 HDR 几何、深度、光照和 SDR 合成出口，再分析分配调用栈所指向的引擎函数。
只有定位出统一设置入口，或完成协调一致的目标 / 视口 / 常量替换，才能实现真正的场景渲染倍率。还需要在全尺寸 UI 合成前使用明确区分输入与输出尺寸的厂商重建接口。
这些步骤尚未完成，不把目标追踪诊断称为已经实现提速。

## 实际场景的分配与视图入口

本轮正常场景记录得到 79 个颜色 / 深度目标、2467 条抽样绘制，涵盖 11 个帧号。
主 HDR 为 RGBA16F，最终场景 / UI 颜色为 RGBA8，均为 1920x1080。HDR 场景与主 UI 共用引擎的 1920x1080 深度目标。
记录中有 81 次绘制把该深度目标作为像素 shader 输入，因此不能只缩小颜色或只替换深度绑定，而忽略深度采样。

只读函数与对象检查确认以下入口，均属于当前版本的定位结果，不是通用游戏 API：

| RVA / 字段 | 观察结果 |
| --- | --- |
| 0x23C4D0 | 主场景渲染函数，读取输出颜色目标宽高并申请 HDR 临时目标 |
| 0x22DE40 | 临时目标池，按格式、宽高和标志查找可复用对象 |
| 0x23EFFB | 最终场景颜色合成绘制的返回位置，随后进入主 UI 提交 |
| 全局 0x7D0CE8 → +0x4F0 | 正常场景拥有者链；虚表槽 +0x30 实际指向 0x23C4D0 |
| 全局 0x7D9380 → +0x28 / +0x30 | 输出颜色 / 共享深度包装对象 |
| 包装 +0x08 → +0x1C / +0x20 | 两个后端对象中观察到的宽高：1920 / 1080 |

可研究的下一步是：只在主场景渲染调用期间提供低尺寸的颜色 / 深度视图，处理相关深度采样，完成后恢复全尺寸输出，再于 UI 前重建。
这里的难点不再是找一个 shader float，而是视图替换、后处理的一致尺寸和厂商重建接口的输入 / 输出分离。
截至只读定位阶段，没有改写这些字段或替换游戏虚函数；后续原型状态见下一节。

`tools/Inspect-RenderAllocation.py` 使用 `pefile` / `capstone` 只读检查指定函数及已观察对象布局。它不会写进程内存、修改 EXE 或处理启动保护。不要把输出的游戏反汇编放进公开仓库。

## 已停用的倍率验证原型

源码保留 `SceneRenderScale` 百分比原型，配置默认 100（关闭），持续执行入口目前被阻断：单独改写百分比不再安装倍率钩子。它不与厂商档位联动，不作为用户功能发布。
仅在 PE 版本、场景虚表位置、渲染函数地址及 32 字节代码指纹同时符合已观察游戏版本时安装对象虚表替身；不改写 EXE 文件或函数指令。

原型调用引擎临时目标池申请低尺寸颜色和深度包装，在主场景函数调用期间替换两者，返回后恢复原输出目标，再用空间放大写回全尺寸场景颜色。
此时仍可能缺少其它后处理资源的尺寸适配，必须检查实际画面；不能仅根据场景入口的位置宣称 UI 全覆盖或后处理一致。

这一步验证“游戏能否真正以较小目标渲染场景”，不是已经完成原生式 DLSS / FSR / XeSS 接入。低尺寸输入直送厂商后端、正确历史、深度 / 运动矢量与锐化仍需后续实现。
现有主场景 AA 回调在该作用域内暂停，避免重建未完成的中间目标，因此不应把空间验证版画质当作最终厂商重建效果。

已完成：1000 次正常 / 异常作用域恢复测试，以及 640x360、1920x1080 的空间输出全覆盖和 DX11 目标 / viewport 状态恢复测试。游戏倍率和画质未验证，不宣称性能收益。
若要撤销本机试验，将 `[KuroUI]` 的 `SceneRenderScale` 设为 100 后重新启动，或恢复备份组件。

首轮游戏验证只创建了 1440x810 的颜色 / 深度目标，主 HDR 仍为 1920x1080，没有完成倍率切换。
原因是把临时池记录当作引擎纹理包装：池记录的 +0 才是引擎包装指针，其 +8 是格式字段，而引擎包装的 +8 才是后端对象。
已修正这层解引用，补充池记录布局 / 作用域恢复回归测试及明确回退日志。修复后的实际游戏效果仍待确认。

修复后的游戏测试确认 HDR、颜色和深度目标均产生了 1440x810 版本，倍率入口确实触发；但出现反相样式颜色异常并逐渐全白，HUD 仍可见。
因此该原型验证失败，已关闭本机倍率设置，并在源码中阻断执行。不能把创建低分辨率目标和恢复两个指针视为渲染链一致性验证，更不能据此宣称提速成功。

具体错误尚未定位。后续需要逐段检查 HDR 有效颜色、曝光输入与历史、色调映射、深度采样和尺寸常量，以及引擎内部的绑定缓存是否与真实 DX11 状态一致。
先恢复原组件，不让用户反复试验未经定位的颜色修补。没有修改游戏 EXE、图形配置或存档。

修复诊断盲区后，另行提供默认关闭的 `SceneScaleCompareOnce` 单次对照入口。持续倍率仍不可用。
它等待 60 次有效主场景调用，记录原倍率一帧，再尝试低倍率一帧，随后撤销触发设置并恢复原倍率调用；不保证错误曝光历史立即恢复，必要时重启游戏。
输出颜色范围 / 非有限值统计，以及视口和候选常量字段。候选常量必须与对应 shader 的参数布局核对，不能只凭字节偏移认定为 `cb_scene`。
单次回读有同步开销，不用于性能测试；对照组件并不代表已修复游戏画质。

单帧对照已确认具体尺寸错配：75% 阶段的实际视口为 1440x810，但几何和第一个目标切换阶段的 `cb_scene.vpSize_g` / `invVPSize_g` 仍对应 1920x1080。已与四个实际 shader 的参数布局逐一核对，不是仅凭偏移猜测。
HDR 抽样均值为原倍率 0.355864、低倍率 0.359948，均未采到负值或非有限值；这不证明所有 HDR 像素正确。
最终颜色的均值从原倍率 0.404116 降到低倍率写回前 0.0395081，写回后为 0.0394614。因此大幅变暗在写回之前已发生，不能归因于最后的空间放大。

已加入按反射布局限定的 GPU 常量副本：只修改视口宽高与倒数，不写游戏原始常量缓冲，也不改 `resolutionScaling_g` 或未经验证的光照字段。场景结束和异常路径恢复原绑定。
测试覆盖精确字段、源缓冲更新、源数据不变和绑定恢复。实际游戏中的颜色修复仍待单帧对照，持续倍率继续关闭。
当前按绘制更新副本是正确性原型，不作性能承诺；若画质验证通过，还需要按源更新代次缓存及完整后处理适配。

修复后的游戏对照确认视口常量已为 1440x810，但最终颜色仍在写回前变暗：原倍率均值 0.403553，低倍率写回前 0.0394772，写回后 0.0393755。
因此尺寸错配修复真实生效，但不足以解释全部异常，不能视为完整画质修复。
下一项限定两帧的记录补充逐绘制资源流、最多 24 组小型全屏后处理输出统计和小尺寸 R32_FLOAT 输入统计，定位首次异常输出，而不是继续猜曝光系数。

逐步骤记录找到了最早异常：`7ce9d3e5de9c057a` 的原倍率输出均值约 0.330083，低倍率输出全零；其读取槽 0 / 1 / 2 在低倍率帧全部为空。
后续亮度归约从原倍率约 0.268268 降到 0.000106042，所以曝光变化是错误输入后的连锁结果，不能只通过调曝光补偿修复。

只读检查该引擎函数确认它同时写入 HDR 颜色和场景对象 `+0x408` 的第二张辅助颜色纹理。原型只缩小前者，后者仍为 1920x1080。
[DX11 文档](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-omsetrendertargets) 要求所有同时绑定的颜色目标尺寸一致。
独立夹具复现混合尺寸绑定被拒绝后，三个源纹理输入被清空；改为同尺寸双输出后，所有三个输入均成功绑定。

已将该辅助输出纳入同一个作用域的低尺寸分配 / 恢复，保持原格式，并加入三目标恢复测试与实际 `OMGetRenderTargets` 输出记录。
GPU 夹具通过，游戏颜色恢复仍待单帧对照。这个修复不代表已经完成全部视图适配或厂商重建接入。

多目标修复后的单帧游戏记录确认三个输入恢复，两个实际输出均为 1440x810。首个后处理均值约 0.333396（原倍率 0.330148），最终颜色约 0.405972（原倍率 0.403326），用户未再观察到闪黑。
这些数值说明此前全零输出问题已消失，不证明所有像素、场景或性能都通过验证。

新增默认关闭的 `SceneScaleContinuous=0` 持续测试入口。本机获确认后以 75% 进行较长场景测试，诊断回读和采集均关闭。
持续版使用 GPU 上的常量副本，恢复全尺寸辅助数据 / 深度，并将放大后的全尺寸颜色交回现有 UI 前 AA 路由。
当前仍是低尺寸场景 → 空间放大 → 现有 AA，未把低尺寸输入直接交给厂商后端；额外常量更新和全尺寸写回可能抵消渲染节省，不承诺帧率提升。
暂不与质量 / 均衡 / 性能档位联动，不作为已发布便携包功能。撤销测试可将 `SceneScaleContinuous=0`、`SceneRenderScale=100` 后重新启动；错误回退会自动关闭入口。

持续测试用户反馈分辨率降低但帧率下降。运行日志未见倍率回退或 DLSS 重复重建，DLAA 仍创建 1920x1080 → 1920x1080 特性。
AeonSR 的内部 GPU 时间约 4.5 ms，其中运动估计约 1.8 ms、DLAA 约 2.17 ms；这些并非游戏整帧时间。

原型逐绘制、逐 VS / PS 重做常量复制与计算 dispatch，属于可确认的重复工作，但尚未单独测得其实际时间占比。
已加入每个视图调用内的副本缓存：源更新、映射 / 解映射或 GPU 复制写入通知会使缓存失效，下一次使用时重新修补；每次视图调用开始也强制失效。
夹具中 404 次请求只执行 2 次 GPU 修补、命中 402 次，并验证源内容更新与游戏缓冲保留。实际游戏计数和 FPS 收益待确认。
即使这部分开销降低，三次全尺寸写回、状态切换和原尺寸厂商 AA 仍存在；不能将该优化描述为完成了原生式重建提速。

## 缓存后仍降帧：分段测量与接入方向

持续模式实测常量缓存命中率约 99.4%，通常每帧两次 GPU 修补，但用户仍观察到帧率下降，关闭倍率后恢复。现有日志没有足够的分段数据，不能据此认定常量、写回或厂商处理中的哪一项占主要成本。

常量副本没有新增工作线程；它在已有 DX11 提交线程上复制缓冲、切换上下文状态并提交计算。缓存命中后仍有逐绘制取缓冲、锁和绑定检查。这是正确性补丁和回退路径，不是最终倍率架构。后续优先寻找引擎统一视图参数生成 / 上传入口，让目标分配、视口和常量一起使用低尺寸；未验证的 `resolutionScaling_g` 不能直接当作 CPU 端倍率开关。

本轮将常量布局查询移到 shader 创建时，并在 shader 绑定时缓存槽位，消除逐绘制的布局查表和相应互斥锁。持续模式不再为已关闭的诊断查询绘制目标资源 / 描述。保留常量更新失效机制、原缓冲保护和三个输出恢复，不宣称已经消除所有逐绘制操作。

新增默认关闭的 `SceneScaleProfileFrames`，取值 1–600，建议 120。启动后先跳过 60 次有效场景调用，再采集指定数量的调用，输出 `KuroAA/KuroUI-scale-timing.csv`。计时仅支持已验证的主场景入口，使用八组异步查询；查询未完成时跳过采样，不等待、不刷新 GPU 队列，不回读颜色或常量。采样完毕停止提交新查询，后续帧继续收取结果。

- 原生基线：保留 `SceneScaleContinuous=0`、`SceneScaleCompareOnce=0`、`SceneRenderScale=100`，只设置采样数。即使遗留了低倍率百分比，单独开启计时也不会开启倍率。
- 低倍率测量：仅在另行确认后启用持续模式。不要与单帧像素对照同时测量；单帧对照的同步读取不适合性能比较。
- CPU：场景提交、倍率绘制回调累计、常量处理累计、辅助 / 深度 / 颜色写回及实际 UI 前 AA 调用。回调和常量耗时包含在场景提交耗时内，不可相加。场景提交计时不包含目标池分配前的准备过程，也不代表整个游戏帧。
- GPU：场景区间、三次写回、目标登记，以及常量复制 / 修补区间的累计。常量 GPU 时间已经包含在场景区间内，每次采样最多记录八次修补；超过后标记 `patch_overflow`，该累计不能当作完整成本。
- AA：`aa_bridge_cpu_ms` 覆盖实际 `render_effects` 调用，包含驱动提交与桥接等待；`aa_d3d11_gpu_ms` 是 DX11 队列上的包围区间。AeonSR 在独立队列上的厂商计算耗时仍需结合其自身日志，不能把 DX11 时间当作厂商 kernel 时间，也不能把这些区间直接相加。当前未进一步拆分桥接等待。
- `valid=0` / `aa_valid=0` 的 GPU 数据无效；`aa_present=0` 表示未关联到该次场景后的 AA 调用。原生模式未执行的三次写回和目标登记字段应忽略。CSV 行按结果就绪顺序输出，应按 `sample` 排序。

独立 GPU 夹具已验证默认关闭不写文件、原生 / 倍率尺寸记录、有限异步采样、修补溢出标记、AA 查询和未走完边界时的收尾；常量夹具仍通过源内容保留与绑定恢复。组件编译通过。尚未替换游戏 DLL 或采集新的游戏计时，未测得 FPS 收益。

AeonSR 接口检查确认现有角色预览入口只有单个颜色资源，桥接以其尺寸创建工作面并将结果复制回同尺寸目标。主场景独立接口需要显式区分输入颜色与输出目标、输入 / 输出尺寸、视图历史及失效条件；仅给现有预览入口传低尺寸颜色不会自动得到全尺寸输出。DLAA 保持原生尺寸，VRS 仍为独立选项。去除辅助 / 深度写回前，仍需证明后续 UI 和其它阶段不再读取它们。

## 低输入 DLSS 直连实验版

新增独立场景接口，配置入口为 `SceneVendorDirect=1`，只作用于已验证版本的 NVIDIA DLSS 非原生档位。输入尺寸来自 NGX 的实际档位查询，不使用另一个手填倍率。DLAA、关闭 AA、其它厂商或全屏规则继续走原有路径。旧的持续倍率试验开关可以保持关闭。

链路为：低尺寸场景颜色 / 深度 → 低尺寸运动估计 → DLSS 全尺寸输出 → 全尺寸 UI。DLSS 直接读取低尺寸颜色，没有颜色预放大或完整第二次 AA。创建特性时明确设置低尺寸运动矢量标志，运动缩放使用实际输入尺寸。视图、输出尺寸或档位变化以及帧号不连续时重置历史。

保留两项必要恢复：辅助数据点采样写回和深度写回。DX11 / DX12 共享面仍需要低尺寸颜色 / 深度各一次复制、重建结果一次全尺寸导出、共享栅栏和提交刷新；这版不是零复制、零同步实现。尺寸常量修补仍使用原缓冲保护副本，但只在布局槽位、相关绑定或已知源数据变化后检查，不再每次绘制取缓冲并查布局。尚未找到可以取代这项修补的统一引擎倍率入口。

锐化暂不额外执行，以避免新增全尺寸处理；管理器保留原锐化值并在直连档位禁用该控件。没有新增投影抖动钩子，移动画面的稳定性和细节质量仍需游戏验证。失败时恢复原目标并重绘原生场景，不把失败输出继续用于 UI。

真实 GPU 夹具在 1920×1080 输出下通过以下输入尺寸：质量 1280×720、均衡 1114×626、性能 960×540。测试覆盖完整直连接口、颜色重建、后叠加 UI 像素不变及 DX11 目标 / 视口不变。夹具通过不等于游戏通过，暂未测得游戏帧率收益。

补充测试通过超级性能 640×360 → 1920×1080，以及均衡 371×209 → 640×360。包含输出范围的网格颜色检查和完整 8×8 UI 区域检查。管理器配置 / 控件自测、三目标异常恢复、多目标同尺寸绑定、常量保护和计时夹具也通过。

本机试用版已按用户要求安装并选为均衡，旧持续倍率和单帧对照均保持关闭。安装仅替换扩展后的 AeonSR、KuroUI 和管理器，保留原运行库、着色器缓存及其它设置，原组件与配置另行备份。该本机安装没有推送、发布或改变便携包的默认开关。游戏画面与帧率尚待实际运行确认。

分段计时继续可选：直连模式的 `color_*` 区间包含重建和导出，不能理解为空间放大时间；其中 AA 包围区间与它重叠，不可相加。AeonSR 的 `scene-direct-perf` 日志单独记录低输入运动估计与 DLSS 的 DX12 GPU 均值。基线与直连均可设 `SceneScaleProfileFrames=120`，一次加载收集该次运行的分段数据。
