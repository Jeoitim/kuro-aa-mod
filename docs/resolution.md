# 分辨率与档位

## 是否需要降低游戏分辨率

不需要。通常保持屏幕原生分辨率，直接在 Mod 中选择 DLAA / Native AA 或 Quality、Balanced、Performance 等档位。

DLAA / Native AA 保持处理目标的输入与输出尺寸一致。其它档位由厂商后端决定内部重建尺寸：游戏先完成渲染，Mod 再缩小颜色图并重建回处理目标的尺寸，不会改变游戏的几何渲染分辨率。

因此，降低档位可能减少 Mod 内部重建的一部分开销，但不会减少游戏本体的几何与着色工作，光流和输出处理也不会随之全部减小。它可能比 Mod 的 Native AA 更省时，但不保证比关闭 Mod 更快，还可能降低细节质量。这些档位不应被当作已经实现的游戏提速功能。

若主动降低游戏分辨率，游戏本身会少渲染像素，但最终输出也会降低，或由游戏 / 显示系统另行放大；这与 Mod 内部档位缩放不同。要实现原生式提速，需要在游戏渲染场景之前降低内部渲染尺寸，再重建到原输出尺寸，并同步适配深度、viewport、后处理和界面合成。目前没有实现这条路径。

## 是否只能使用 1080p

不是。主场景读取实际颜色纹理的尺寸，厂商后端按它创建输入、输出及历史资源。1080p 是作者的测试环境，不是硬编码的输出尺寸。

场景纹理与窗口尺寸可能不同。引擎边界规则可处理已确认的独立场景目标；Shader 签名规则的尺寸检查可能使某些非标准布局跳过 AA。最终游戏输出尺寸仍由游戏决定。

1440p / 4K 的处理和显存开销更高，完整游戏画质、性能和全部宽屏布局尚未验收。不能把“代码按实际尺寸处理”当作所有分辨率都已测试通过。

## 分辨率切换与角色缓存

ReShade 6.8 在交换链尺寸改变时调用 runtime 销毁 / 初始化事件。KuroUI 在销毁事件中释放角色厂商上下文和透明度缓存；主场景由 AeonSR 的交换链 / 尺寸检查重建资源与历史。

所以普通窗口 / 游戏输出分辨率切换不会永久保留上一分辨率的角色缓存。切换过程中以及首次重建时可能有短暂停顿。

已提交的固定预算以 8,294,400 像素为上限，约等于四张 1080p 或一张 4K 纹理。后续开发版本已改为可调的 MB 估算预算与数量上限，并可查询可用显存；两项都满足才会新增缓存。这只限制角色缓存，不限制主场景 AA。

如果每个角色纹理都为 3840x2160，固定像素预算只容一个这样的上下文。可调预算版本考虑了额外开销，默认 512 MB 甚至可能拒绝这样的单实例，需要提高预算且满足可用显存约束。同尺寸模型可以复用已退还的上下文。
游戏输出为 4K 不表示立绘纹理也是 4K。已观察到的角色纹理有 512x512、1024x1024 和 1920x1080 三种尺寸，合计 3,384,320 像素，可以同时放入当前预算。
固定预算对高分辨率、多视图覆盖较保守；后续可以考虑可配置预算或按实际显存自适应，但不应为了覆盖更多模型而引入显存换页卡顿。
预览纹理还需满足单采样、单层、单 mip、RGBA8 / BGRA8、宽高不超过 4096 等条件。超过预算或不符合条件的模型保持原画面，不会为了覆盖所有模型而在对话帧内淘汰缓存。

如果游戏只改变内部渲染比例、却不重建输出交换链，角色缓存仍采用有界复用策略；出现额外尺寸时可能跳过处理。重启游戏会清空缓存。

## 能否保存缓存，让下次启动不再初始化

可以保存编译结果，不能直接恢复上一进程的显卡上下文、纹理句柄和厂商特征句柄。时域历史也必须从当前画面重新积累，否则会把上次运行的内容带入当前画面。

上游 AeonSR 的 FSR / XeSS 已有本地管线缓存与预构建路径，使用这些后端时可以减少部分编译工作。当前光流初始化仍调用 D3DCompile，后续可缓存其着色器字节码，并在同一设备的视图之间复用适当的编译结果或管线。

本地缓存、加载阶段预热和非阻塞初始化是可行的优化方向，但仍需要每次创建设备资源和厂商实例，不能承诺下次启动完全无停顿。缓存还需按代码、编译参数、运行库、显卡和驱动等条件检查兼容性，更新后可能需要重建。
