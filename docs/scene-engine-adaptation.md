# 场景适配逆向结果

本文保留入口定位与夹具结果，面向开发者。当前使用说明见 [README](../README.md)，规则是平行选项，不能用这份定位记录判断画质高低。

## 已确认

游戏构建：云豹版 ed9.exe，SHA256
`91ff6a7ffe68326525537c091d62d30053517c483c6cc2dea33a34a76fc56909`。

只读 RTTI 分析找到 14 个相关类型、12 个虚函数表。正常 Steam 启动后的代码分析得到
35 个虚函数表引用和 20 个相关直接调用。没有修改游戏程序或启动保护。

引擎 Draw / DrawIndexed 包装函数 RVA 分别为 0x443030 / 0x443050。
实际批量绘制也使用其它通用 RendererDX11 入口，所以不能用“调用了 Draw”识别 3D 场景。
场景、阴影和 UI 都经过共用的提交函数 0x3DCE70、0x3D80E9。

当前普通场景的 UI 提交路径包含 0x37F480，而已采样的场景几何、阴影和后处理未包含它。
该函数的 32 字节运行时代码 FNV64 为 0x533EBF8BA7423D58。
它是已观察的 UI 批提交候选，不是全部 UI / 战斗路径覆盖证明。

## 当前路线的实际缺口

当前场景的主颜色目标为 1920x1080，包含 HDR 几何与 SDR 合成阶段。
窗口扩大到 2400x1080 后，最终输出与主场景目标不同尺寸，正式版本的严格尺寸检查会跳过 AA。

一次记录中主 UI 的不同 shader 在 draw 138 已开始，而已有 shader 签名到 draw 158 才命中。
同一签名也用于 256x256 UI 目标，因此签名或 C++ 类型本身都不足以确认主场景边界。

装备 / 换装中的角色展示不能仅凭肉眼“没有 AA”确认是哪个阶段遗漏。
独立 3D 视图、UI 后提交的 3D 元素和缺少正确抖动都需要区分。
当前主场景实验路线没有完成这些视图的适配。

## 已实现的实验原型

原型以经过 PE 时间戳、image size 和代码指纹验证的引擎函数上下文判断主 UI，
跟踪最大的有效几何颜色目标，在该目标的 UI 提交前运行 AA。
不依赖 pixel / vertex shader 签名，允许场景目标与输出窗口尺寸不同。
该路径处理一个主场景，不覆盖独立角色展示。角色界面的单独处理见 [实验功能](vendor-preview.md)。

自动夹具采用独立、不内联的 UI 提交函数，场景 640x360，输出 800x360：

| 后端 | UI 不同像素 | 场景不同像素 | 引擎路径 |
| --- | --- | --- | --- |
| DLAA | 0 | 41485 | 执行 |
| FSR | 0 | 48100 | 执行 |
| XeSS | 0 | 46397 | 执行 |
| 错误函数指纹 | 0 | 0 | 安全跳过 |

这些测试证明路由、尺寸和回退行为，不证明游戏战斗或所有预览画质。

## 根本解决方向

需要在通用 3D 渲染视图生命周期中识别“视图完成”事件，建立稳定视图身份，
按视图关联最终颜色、深度、相机和历史，再在 UI 合成之前处理。

正式依赖存在两项实际限制：ReShade 6.8 的 render_effects 每帧只执行一次；
AeonSR v1.0.1 的 App 使用单套 FrameHistory 与 optical-flow 状态。
因此不能反复调用同一个入口，把不同相机 / 尺寸的历史混在一起。

后续需要扩展厂商重建的按视图上下文及显式处理入口，而不是持续追加界面 shader 签名。
在处理多视图前，还需区分阴影、反射、粒子辅助目标与真正可展示的 3D 视图；不能对所有 3D draw 做 AA。
